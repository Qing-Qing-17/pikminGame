# pikminGame

皮克敏主題的遊戲，細胞分裂與戲精酒吧。

由指揮官（主持人）投影或自用一台裝置，參加者用手機掃同一個網頁、輸入房間代碼加入。
兩種活動流程：

- **星攻略**：皮克敏迫降 → 偽裝洞穴
- **培訓**：皮克敏迫降 → 情報交換 → 偽裝洞穴

線上版：<https://qing-qing-17.github.io/pikminGame/>

> ⚠️ **目前多人連線無法使用。** 同步所依賴的第三方服務 kvdb.io 已連不上，
> 輸入房間代碼會失敗，指揮官畫面也會顯示「連不上同步伺服器」。
> 詳見下方〈多人同步〉與〈更換同步後端〉。

## 執行方式

`index.html` 是原始碼，直接用瀏覽器打開就能跑（JSX 在瀏覽器裡即時編譯，
需要能連到 cdnjs 與 cdn.tailwindcss.com）。

正式活動請改用建置版：

```bash
npm install
npm run build      # 產出 dist/index.html
```

`dist/index.html` 把 JSX 預先編譯、Tailwind 產成靜態 CSS、React 直接內嵌，
不依賴任何 CDN，載入也快得多（可互動時間約 2.1s → 1.4s）。部署時上傳這一個檔案即可。
唯一的外部資源是 Google Fonts；被擋掉時會退回系統字型，不影響功能。

## 發佈到 GitHub Pages

`.github/workflows/deploy.yml` 會在推上 `main` 時自動建置並發佈 `dist/`，
網址是 `https://<帳號>.github.io/pikminGame/`。

流程裡的 `actions/configure-pages` 帶了 `enablement: true`，Pages 沒開啟時它會直接
用 API 開起來，所以**不需要手動到 Settings 設定**。若那一步失敗（例如組織政策擋住），
再到 **Settings → Pages → Build and deployment → Source** 選 **GitHub Actions** 即可。

發佈的是建置版，不是根目錄的原始碼——原始碼要在瀏覽器裡即時編譯 JSX，
現場用手機開會明顯變慢，而且一旦連不到 cdnjs 就整頁打不開。

## 多人同步

### 目前狀況

狀態原本存在 [kvdb.io](https://kvdb.io) 的一個 bucket，房間代碼就是 bucket 代號，
各裝置以輪詢同步。**這個服務現在連不上**，因此：

| 功能 | 是否可用 |
| --- | --- |
| 選擇活動、故事、指揮官的所有畫面 | ✅ 可用 |
| 皮克敏迫降（集合人數、倒數、音樂） | ✅ 可用——這一關本來就只需要指揮官那台裝置 |
| 用「測試：進入皮克敏介面」在同一台裝置試玩 | ✅ 可用 |
| 參加者用手機輸入房間代碼加入 | ❌ 連不上 |
| 情報交換、偽裝洞穴（需要每個人各自的裝置） | ❌ 連不上 |

要確認是不是服務本身的問題，用手機瀏覽器直接開 <https://kvdb.io/>：
網站本身打不開就代表服務已經停止，不是這個專案的設定問題。

### 同步層做了什麼

因為 kvdb 是一個公開的鍵值儲存、沒有原子操作也沒有存取控制，同步層做了幾件事來撐住現場：

- 寫入前先讀最新值、只套用自己的異動、寫完再讀回驗證，失敗則指數退避重試。
- 指揮官的寫入一律從遠端保留玩家資料，只有明確重置的動作才覆蓋。
- 每次輪詢比對「自己送出過的東西還在不在」，不在就補寫回去（自我修復、最終一致）。
- 同一台裝置的寫入串成佇列，避免亂序抵達讓關卡倒退。
- 畫面切到背景時停止輪詢；狀態沒變化時逐步拉長間隔。

**已知限制**：房間沒有存取控制，知道代碼的人都能讀寫，參與者也可透過開發者工具
竄改狀態。指揮官會保留本機備份並在資料被清空時自動還原，但無法防止針對性的竄改——
那需要一個真正的後端。假情報的答案不會上傳，只留在本人的裝置上並由該裝置判定對錯。

## 更換同步後端

### 要改哪裡

所有對外的網路呼叫都集中在 `index.html` 的「kvdb.io 同步」區塊，只有五個函式：

| 函式 | 作用 |
| --- | --- |
| `createBucket()` | 開一個新房間，回傳房間代碼 |
| `probeReachable()` | 判斷服務是否連得上（用來顯示警告） |
| `kvRead(bucket, key)` | 讀取，並區分「確實不存在」與「連線失敗」 |
| `kvGet(bucket, key)` | `kvRead` 的簡化版 |
| `kvSet(bucket, key, value)` | 覆寫 |

其上的 `kvMutate`（讀取－合併－寫入－驗證－重試）與所有畫面邏輯都不碰網路，
換後端時不需要動。換成另一個 HTTP 鍵值服務約是改這五個函式；
換成即時資料庫則可以連輪詢一起拿掉。

### 評估過的選項

**建議：Firebase Realtime Database。**

- 免費方案（Spark）對這個規模綽綽有餘：100 個同時連線、1 GB 儲存。
- **即時推播，不需要輪詢**——現在那一整套「讀取－合併－寫入－驗證－重試」加上自我修復，
  都是為了硬撐一個沒有原子操作的鍵值儲存。RTDB 支援對單一路徑寫入與 `transaction()`，
  兩個人同時寫不同欄位根本不會互相覆蓋，問題從結構上消失而不是靠重試補救。
- 用戶端設定（apiKey 等）本來就設計成公開，放在靜態頁面裡是正常用法；
  存取控制走安全規則，可以真正限制「誰能改哪個房間」——這是目前做不到的事。
- 代價：需要一個 Google 帳號、建專案、開啟 Realtime Database、貼上設定。
  手機上做得到但頁面很擠，建議用電腦。

**次選：Supabase。** 同樣有即時同步、anon key 公開、Row Level Security。
設定比 Firebase RTDB 多一點（要建表與政策），而且免費方案的專案在長期閒置後會暫停——
若活動在幾週後才辦，記得先喚醒。

**最穩但最費工：Cloudflare Workers + Durable Objects。**
真正的原子協調與 WebSocket，免費額度充足，可以做到完整的權限控管。
但要有 Cloudflare 帳號並部署一個 Worker，前置作業最多。

**不建議：再找一個免註冊的鍵值服務**（jsonbin、npoint 之類）。
改動最小，但這正是這次出事的模式——免費免註冊的服務說停就停。
而且多數要在頁面裡放 API key，等於任何人都能清空全部資料。

**不適用：純 P2P（WebRTC / PeerJS）。** 仍然需要一台信令伺服器，
公開的那些不夠可靠，而且遲到的人拿不到既有狀態。

### 尚未實測

以上都**沒有**在這個專案裡實作或驗證過。開發環境的出口代理封鎖了外部網域，
無法從這裡連到任何候選服務，因此不論換成哪一個，都必須部署到線上網址後親自測過
才能用在正式活動上。
